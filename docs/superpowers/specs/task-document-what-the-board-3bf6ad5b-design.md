## Observable result

README section covers, in order:

- **Events → card.** A table matching B2: subtask done / escalated / cancelled → the subtask; merged base failed → the story the base roots; run end → the milestone card; `am run --card` run end → the subtask only (no milestone card). A sentence listing what is not posted: started, per-phase, retries, revision loops, gate warnings, subtasks parked because another card escalated (the run-end comment lists them), pause on subtask cards.
- **One example body per comment type** (done, escalated, cancelled, base failed, run end), each a fenced block with first line `am · <outcome> · run <run-id>`, commands in backticks, card ids as `[[id]]`, and last line `am-key: <run-id>/<card-id>/<event>`. Field lines are taken from the actual `compose_*` output (e.g. generated by reading the composers / the 649a8e88 golden expectations), with placeholder ids.
- **Who writes them.** Author `am`; code composes every body; agent text appears only from the three failure fields (validate_spec/validate_plan `reason`, implement `blocked_reason`, review `unresolved_blockers`), double-quoted, `[[` rewritten to `[ [`, cut first when the body would exceed 1,500 characters, followed by `… (truncated; see `am logs …`)` (exact marker as built).
- **The `am-key` trailer.** Key format and event names (`done`, `escalated:<lease-token>`, `cancelled`, `base-failed`, `run-end:<lease-token>`); why: flush checks the card for the key before posting, so crashes, replays and resumes never double-post; each life of a resumed run gets its own escalation and run-end comment.
- **Best-effort.** Comments are queued in the store after the outcome is recorded and posted afterwards; a `brd` failure or timeout never escalates, parks or changes run status — it becomes a report warning, the row stays pending and is retried on the next flush (run end, `am resume`, relaunch); after `COMMENT_ATTEMPTS` failures the row is abandoned with one warning. Warning wording quoted from `comments._warning` as built.
- **Nothing is deleted.** The thread is append-only: an escalation comment stays after a later resume appends `done (resumed at <phase>)`; `am` never edits, supersedes or deletes comments and never reads them back to decide anything (the board is not a second source of truth).
- A one-line pointer to §7 Deferred of the board-comments addendum, matching how earlier README sections link their addenda.

D5 row: the sentence "`brd` receives status transitions only." becomes "`brd` receives status transitions and a bounded set of code-authored, append-only, idempotent outcome comments. `am` never reads comments back to decide anything: the board is not a second source of truth."
